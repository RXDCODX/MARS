# План: автоматическое обнаружение и отображение Twitch-наград

**Ветка:** `feat/reward-alert-activation`  
**Цель:** создание обычной Channel Points-награды в Twitch должно автоматически приводить к событию в MARS и отображению в ClientApp. Для стандартной награды не должно требоваться добавлять `AlertKey`, константу, серверный класс, клиентский switch или отдельную регистрацию.

## 1. Как должно выглядеть использование

### Обычная новая награда

1. Стример создаёт Channel Points reward в Twitch — через Twitch или страницу управления наградами MARS.
2. Зритель активирует награду.
3. MARS автоматически получает событие и показывает стандартный алерт: название награды, зрителя, стоимость и текст активации.
4. Никаких изменений кода, `AlertKey` и ручной регистрации не требуется.

Если к награде привязано медиа в MediaStorage, стандартный алерт дополнительно показывает это медиа. Без привязанного медиа он всё равно отображается как обычная карточка, а не пропадает.

### Награда с особым поведением

Для действий, которые нельзя вывести из обычного редемпшена (например, закрыть игру, запустить Random Art, ограничить активации Miku/Fumo или запросить возврат баллов), остаётся отдельная серверная логика. Но это исключение для специальных возможностей, а не обязательный шаг для каждой новой награды.

## 2. Что сейчас мешает

1. `ChannelRewardDefinition.AlertKey` обязателен. Новый элемент каталога наград должен заранее знать ключ алерта.
2. `ChannelRewardsManager.UpsertLocalAsync` и `SyncRewardServicesToLocalAsync` ищут запись по `AlertKey`. Это связывает запись Twitch-награды с программным идентификатором рендера.
3. `RewardRedemptionPublisher` ищет локальную запись по Twitch reward ID или названию, извлекает из неё `AlertKey`, а при пустом ключе прекращает обработку. В результате обычная награда, созданная непосредственно в Twitch и не имеющая локальной записи/ключа, может вообще не попасть в общий поток активаций.
4. `RewardActivatedConsumer` также пропускает события без `AlertKey`.
5. В ClientApp обработчик `RewardActivated` пока заглушка `() => undefined`. Серверный контракт и эффекты сами по себе ещё не дают видимого результата в браузере.
6. `RewardDayRules` использует `AlertKey` как идентификатор специальных дневных правил. Эти ограничения нужно отделить от идентификатора обычной награды.
7. Поиск медиа должен опираться прежде всего на однозначную привязку к Twitch reward ID. Нельзя считать стоимость уникальным идентификатором: у двух наград могут совпадать баллы. Также нужно проверить тип `TwitchRewardId` и не предполагать, что строковый ID Twitch можно безопасно преобразовать в `Guid`.

## 3. Целевая архитектура

### 3.1. Twitch reward ID — техническая идентичность

Использовать `TwitchRewardId` как основной стабильный идентификатор награды. Это ID из Twitch EventSub, а не название, стоимость, эмодзи или `AlertKey`.

Название, prompt, стоимость, пользовательский ввод и автор активации — данные события для отображения. Они не должны определять маршрут сообщения.

`AlertKey` не должен быть обязательным полем для создания, синхронизации или отправки обычной награды. В первом этапе его можно оставить только как временный compatibility-механизм для существующих специальных эффектов; затем удалить из основного контракта и UI.

### 3.2. Не терять неизвестную MARS награду

`RewardRedemptionPublisher` должен публиковать каждое валидное событие `channel.channel_points_custom_reward_redemption.add`, даже если локальная запись не найдена и нет специального эффекта.

Минимальный payload активации должен содержать:
- уникальный ID редемпшена/EventSub message ID для дедупликации;
- Twitch reward ID и актуальное название награды;
- Twitch user ID, login/display name;
- стоимость и user input;
- время активации;
- необязательное медиа;
- необязательные данные специального эффекта.

Отсутствие записи в локальной БД, `AlertKey` или специального эффекта не является причиной отбрасывать событие. В таком случае используется стандартное поведение.

### 3.3. Автоматический каталог наград

Добавить reconciliation/sync Twitch reward catalog:

- получать список актуальных Channel Points rewards через уже существующий TwitchCore/Helix клиент;
- создавать или обновлять локальную запись по `TwitchRewardId`;
- сохранять локальные MARS-настройки и привязку медиа при повторной синхронизации;
- не создавать отдельную запись при каждом редемпшене;
- корректно обрабатывать награды, созданные вне MARS, переименованные и удалённые в Twitch.

Каталог полезен для настроек и медиа-привязок, но доставка события не должна зависеть от того, успела ли пройти синхронизация: EventSub payload уже содержит данные, достаточные для стандартного алерта.

### 3.4. Один стандартный рендерер в ClientApp

Реализовать обработчик `RewardActivated` в ClientApp вместо текущей заглушки.

Он должен:
- принимать неизвестные ранее Twitch reward ID без обновления TypeScript-кода;
- показывать название награды, имя зрителя, цену и пользовательский ввод;
- отображать вложенное медиа, если оно есть;
- иметь безопасный fallback для пустого/неизвестного payload;
- иметь очередь, время показа и дедупликацию по ID редемпшена;
- не зависеть от перечня `RewardAlertKeys`.

Таким образом, добавление новой обычной Twitch-награды не требует нового React-компонента. Один универсальный компонент показывает все новые награды.

### 3.5. Опциональные специальные эффекты

Сохранить `IRewardActivationEffect` для поведения, которое действительно требует серверного кода. Но разделить два понятия:

- **факт активации** — всегда проходит через универсальный поток;
- **дополнительный эффект** — подключается только для известных специальных наград.

Специальный эффект не должен владеть отправкой базового события и не должен блокировать его только потому, что эффект не найден. Он может обогатить событие медиа/данными, выполнить side effect или явно подавить стандартный показ по осознанному правилу.

Для уже существующих специальных наград допустим временный внутренний mapping по стабильному Twitch reward ID или отдельной конфигурации built-in rewards. Не требовать такого mapping для произвольной новой награды пользователя. Не использовать отображаемое название Twitch как скрытый идентификатор — его можно переименовать, локализовать или снабдить эмодзи.

### 3.6. Медиа-привязки

- Первичный способ — однозначная связь `TwitchRewardId -> MediaInfoId` в локальной записи/настройках.
- Если привязка отсутствует, отправлять стандартный алерт без медиа.
- Совпадение по стоимости разрешать только как legacy fallback и только когда найден ровно один кандидат; при нескольких совпадениях медиа не выбирать наугад.
- Не использовать неявное совпадение по названию в качестве основного механизма.
- Проверить существующую семантику `MediaInfo.MetaInfo.TwitchGuid` и тип Twitch reward ID до сохранения старого пути через `Guid.TryParse`.

## 4. План реализации по этапам

### Этап A — контракт и доставка

1. Зафиксировать единый payload активации с `RedemptionId/EventId`, `TwitchRewardId`, `RewardTitle`, данными пользователя, cost, input, timestamp и необязательными media/effect data.
2. Сохранить совместимость protobuf: не переиспользовать номера полей. Сверить контракт с параллельной веткой EventSub/PR #15; в обеих ветках сейчас есть риск конфликта поля `TelegramusEvent.oneof` №37.
3. Изменить `RewardRedemptionPublisher`: событие публикуется и без локальной записи/специального ключа.
4. Оставить один маршрут RabbitMQ для reward activation. Raw EventSub dispatcher продолжает пропускать redemption, чтобы не показывать одно событие дважды.
5. Добавить тесты: неизвестная MARS награда, локальная награда без специального эффекта, переименование награды, повторная доставка одного EventSub message.

### Этап B — автоматический каталог

1. Синхронизировать Twitch rewards с локальным каталогом по Twitch ID.
2. Сохранить пользовательские настройки и media association при sync.
3. Отвязать upsert и поиск записи от обязательного `AlertKey`.
4. Проверить сценарии создания награды через Twitch UI и через страницу управления MARS.
5. Отделить сезонные/дневные правила встроенных наград от общего каталога.

### Этап C — универсальное отображение

1. Реализовать клиентский обработчик `RewardActivated`.
2. Добавить generic reward card и отображение вложенного media.
3. Убрать заглушку `RewardActivated: () => undefined`.
4. Добавить клиентские тесты для незнакомых reward ID, отсутствующего media, user input и дедупликации.
5. Проверить весь маршрут TwitchCore → RabbitMQ → MARS.Alerts → TelegramusEvent/gRPC broadcaster → HubEventRelay → SignalR → ClientApp.

### Этап D — специальные награды и удаление обязательных ключей

1. Перевести существующие особые награды на optional effect mapping по стабильной идентичности/конфигурации.
2. Перенести `RewardDayRules` на внутренние правила встроенных наград, не требующие наличия ключа у каждой записи.
3. Перевести текущие медиа- и клиентские эффекты на новый базовый payload.
4. Удалить обязательность `AlertKey` из `ChannelRewardDefinition`, локального upsert, DTO/UI и пути публикации.
5. После compatibility-периода удалить колонку/константы `RewardAlertKeys`, если они больше не нужны для специальных сценариев.

## 5. Проверки и критерии готовности

- Создать новую награду прямо в Twitch, не добавляя код, ключ, запись вручную или клиентский обработчик.
- Активировать её и получить в ClientApp стандартную карточку с названием, пользователем и стоимостью.
- То же самое должно работать для награды, созданной через интерфейс MARS.
- Переименование награды в Twitch не меняет её идентичность и не ломает доставку.
- Повторный EventSub delivery не показывает один и тот же redeem второй раз.
- Существующие специальные награды продолжают выполнять свои эффекты.
- При отсутствии media или special effect активация не теряется.
- Один redeem не вызывает одновременно generic EventSub alert и reward activation alert.
- В RabbitMQ нет старых активных consumers/bindings, из-за которых одно событие обрабатывается двумя поколениями конвейера.

## 6. Что не должно стать новым обязательным ритуалом

Для обычной новой награды запрещено требовать:
- добавление значения в `RewardAlertKeys`;
- новый `AlertKey` в БД;
- новый `ChannelRewardDefinition` только ради показа карточки;
- новый серверный handler;
- новый protobuf oneof case;
- новый SignalR event name;
- новый TypeScript switch/React component;
- ручное изменение маршрута RabbitMQ.

Новый серверный эффект или особая анимация, конечно, требуют реализации соответствующего поведения. Но простой факт «зритель активировал ещё одну награду Twitch» должен работать автоматически.
