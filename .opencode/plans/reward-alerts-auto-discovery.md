# Итоговый план: универсальная передача Twitch EventSub JSON

**Ветка:** `feat/reward-alert-activation`  
**Связанные изменения:** EventSub transport, Channel Points rewards, TelegramusHub и ClientApp.

## 1. Главный принцип

MARS не должен знать C#-тип каждого Twitch EventSub-события только ради его передачи в браузер.

Twitch присылает JSON-конверт. MARS сохраняет его как JSON, передаёт по единому транспортному маршруту и отдаёт ClientApp. Клиент разбирает конверт и при необходимости интерпретирует `metadata.subscription_type` и `payload.event`.

**Не преобразовывать каждое событие в отдельный C# DTO, не держать реестр `string -> Type` и не создавать отдельный метод TelegramusHub или protobuf-событие для каждого вида Twitch-уведомлений.**

Целевая цепочка:

```text
Twitch EventSub
    ↓ raw JSON
MARS.TwitchCore
    ↓ один RabbitMQ маршрут
RabbitMQ
    ↓ raw JSON
MARS.Alerts
    ↓ общий механизм передачи событий
Telegramus / SignalR
    ↓ raw JSON
ClientApp
    ↓ JSON.parse + разбор metadata.subscription_type
Универсальный обработчик / нужное отображение
```

## 2. Приём EventSub в TwitchCore

### Что изменить

1. Получать исходный JSON на уровне, где он ещё не преобразован TwitchLib в конкретный C# event-класс.
2. Передавать исходную строку дальше без пересборки JSON из C#-модели.
3. Для технической маршрутизации читать только общие поля конверта, например:
   - `metadata.message_type`;
   - `metadata.message_id`;
   - `metadata.subscription_type`;
   - `metadata.subscription_version`;
   - `metadata.message_timestamp`.
4. Для чтения этих полей использовать `JsonDocument` или `Utf8JsonReader`. Не десериализовать `payload.event` в отдельные Twitch-модели.
5. Управляющие сообщения WebSocket (welcome, keepalive, reconnect и прочие control messages) обрабатывать на транспортном уровне. В поток пользовательских уведомлений передавать именно EventSub notifications.
6. Неизвестный `subscription_type` не считать ошибкой: если это валидное notification, он должен пройти дальше без знания его схемы в MARS.

### Что удалить

- `ConcurrentDictionary<string, Type> _eventTypes`;
- инициализацию словаря с `typeof(TwitchChannelRaidEvent)`, `typeof(TwitchStreamOnlineEvent)` и остальными классами;
- десериализацию notification в отдельные TwitchLib event-классы в общем конвейере;
- диспетчеризацию, которая требует добавлять C#-тип для каждого нового `subscription_type`.

### Что не удалять автоматически

Строковые константы `TwitchEventSubTypes` могут оставаться там, где они реально нужны для **создания Twitch-подписок** (название типа и версия подписки). Это не реестр типов для десериализации. Удалять сами TwitchLib-модели можно только после проверки, что они больше нигде не используются.

## 3. RabbitMQ: один маршрут для Twitch EventSub

1. Использовать один общий маршрут, например существующий `twitch.eventsub.raw`.
2. Тело сообщения — исходный JSON EventSub без преобразования.
3. Для технической корреляции и дедупликации передавать `metadata.message_id` в AMQP MessageId/header, не меняя содержимое тела.
4. Не создавать routing key вида `twitch.eventsub.follow`, `twitch.eventsub.raid`, `twitch.eventsub.vip` и т. п.
5. Сохранить корректные ack/retry/error handling. Повторная доставка сообщения не должна приводить к повторному показу одного события.

Тип события можно извлечь из JSON на стороне потребителя. Он не должен определять отдельную очередь или C#-тип.

## 4. MARS.Alerts: прозрачная пересылка

1. Оставить один consumer общего EventSub JSON-маршрута.
2. Consumer передаёт JSON дальше, не преобразуя его в отдельные DTO и не создавая отдельные alert-сообщения для Follow, VIP, Raid, StreamOnline и других типов.
3. Неизвестные типы проходят тем же маршрутом.
4. Не добавлять в общий транспорт бизнес-правила отображения. Задача Alerts в этом потоке — доставка, а не интерпретация каждого Twitch-события.

Если отдельным событиям нужны серверные side effects, их можно выполнять отдельными обработчиками того же входящего сообщения. Такие обработчики не должны создавать вторую копию пользовательского события.

## 5. TelegramusHub и protobuf: один общий транспорт

1. Не добавлять методы вроде `FollowAlert`, `VipAlert`, `RaidAlert`, `RewardActivated` или отдельные методы для других Twitch-событий.
2. Использовать уже существующий общий механизм передачи событий в TelegramusHub / SignalR, если он позволяет передать JSON.
3. Если текущий контракт не умеет переносить произвольный JSON, расширить **общий конверт** одним универсальным полем для JSON (и при необходимости source/message ID), а не добавлять новый protobuf oneof case для каждого Twitch event type.
4. Не вводить отдельный типизированный `TwitchEventAlert` и отдельный типизированный `RewardActivated` как параллельные способы доставки одного Twitch EventSub.
5. При изменении protobuf согласовать номера полей с PR #15. Не переиспользовать номера уже опубликованных полей; отдельно устранить известный конфликт field number 37 между EventSub- и reward-изменениями.
6. Сохранить одну SignalR точку входа для Twitch EventSub JSON. Имя/контракт должны быть общими, а не зависеть от `subscription_type`.

## 6. ClientApp: разбор JSON на клиенте

1. Получать один JSON payload через общую SignalR точку входа.
2. Выполнять `JSON.parse` и читать `metadata.subscription_type`, `metadata.message_id` и `payload.event`.
3. Не требовать от сервера C# DTO или отдельного события для каждого Twitch-типа.
4. Сделать общий dispatcher/обработчик, который может передать JSON нужному клиентскому представлению.
5. Неизвестный тип не должен ломать обработку остальных сообщений. Для него допустим универсальный fallback или игнорирование отображения с диагностическим логом; сам транспорт при этом уже успешно доставил событие.
6. Дедуплицировать сообщения по `metadata.message_id`, чтобы повторная доставка не создавала второй алерт.

**Граница автоматизации:** новый тип EventSub будет автоматически проходить через сервер и SignalR без изменения C# и protobuf. Чтобы красиво отобразить уникальные поля нового типа, может понадобиться клиентский шаблон. Для неизвестного типа должен оставаться общий fallback; транспорт не должен требовать нового обработчика.

## 7. Channel Points: это такой же EventSub, а не второй транспорт

Событие `channel.channel_points_custom_reward_redemption.add` передаётся через тот же raw JSON pipeline, что и любое другое Twitch notification.

### Удалить из базовой доставки

- отдельную публикацию `twitch.reward.activated`, если она дублирует тот же EventSub;
- отдельный `RewardActivated` protobuf/SignalR event как второй канал доставки;
- зависимость публикации от `AlertKey`;
- требование находить локальную запись награды перед отправкой события;
- отбрасывание redemption, если для него не найден специальный обработчик или медиа.

ClientApp получает обычный EventSub JSON и для Channel Points читает из `payload.event` данные награды, пользователя, стоимости и `user_input`. Стандартный показ не зависит от того, создана ли награда через MARS или напрямую в Twitch.

### Логика особых наград

Особое поведение (например, запуск эффекта, ограничения или возврат баллов) может остаться на сервере как дополнительная бизнес-логика, подписанная на тот же EventSub notification.

- Side effect не является отдельным способом доставки события в браузер.
- Отсутствие специального обработчика не блокирует стандартное отображение.
- Для идентификации специальной награды использовать стабильный Twitch reward ID или явную конфигурацию, а не отображаемое название и не обязательный `AlertKey`.
- Не допускать повторного выполнения side effect при повторной доставке одного `message_id`.

## 8. Каталог наград, AlertKey и медиа

Каталог локальных наград нужен для настроек MARS, но не должен быть условием доставки EventSub.

1. Использовать `TwitchRewardId` как идентификатор награды в локальном каталоге.
2. При синхронизации обновлять записи по Twitch ID и сохранять пользовательские настройки.
3. Убрать зависимость `UpsertLocalAsync` и синхронизации от обязательного `AlertKey`.
4. Убрать обязательный `AlertKey` из `ChannelRewardDefinition`, DTO и UI. Временную совместимость оставить только там, где она ещё нужна существующим специальным эффектам.
5. Сезонные и дневные правила встроенных наград отделить от общего идентификатора события.
6. Привязку медиа делать по `TwitchRewardId -> MediaInfoId`. Если медиа не найдено, событие всё равно показывается.
7. Не использовать совпадение стоимости как надёжную идентичность. Legacy fallback по стоимости разрешать только при ровно одном совпадении; при неоднозначности медиа не выбирать.
8. Проверить тип и семантику `MediaInfo.MetaInfo.TwitchGuid` до сохранения существующего пути через `Guid.TryParse`.

Каталог и медиа могут обогащать представление события, но не должны менять исходный Twitch JSON или создавать второй alert. Если для отображения требуется серверное обогащение, передавать его как необязательное расширение общего envelope, сохраняя исходный EventSub JSON доступным без изменений.

## 9. План реализации по этапам

### Этап A — инвентаризация и raw capture

1. Найти текущую точку приёма EventSub и определить, как получить raw JSON до типизированной десериализации TwitchLib.
2. Проверить все использования `_eventTypes`, `TwitchEventSubTypes` и Twitch event-моделей.
3. Реализовать общий raw notification handler.
4. Добавить тесты на известный и неизвестный `subscription_type`, control messages и сохранение исходного JSON.

### Этап B — единая серверная доставка

1. Перевести публикацию Twitch EventSub на один RabbitMQ маршрут с raw JSON body.
2. Перевести MARS.Alerts на прозрачную пересылку.
3. Подключить существующий общий транспорт TelegramusHub/SignalR; при необходимости расширить только общий envelope.
4. Удалить типизированный EventSub dispatcher из базового пути доставки.
5. Согласовать protobuf с PR #15 и убрать конфликт номеров полей.

### Этап C — ClientApp

1. Подключить одну SignalR точку входа для Twitch EventSub JSON.
2. Добавить общий JSON parser/dispatcher и дедупликацию по message ID.
3. Реализовать стандартное отображение Channel Points redemption.
4. Добавить общий fallback для неизвестного типа.
5. Перевести нужные существующие клиентские отображения на чтение исходного EventSub payload. Не реализовывать отдельные серверные методы для каждого события.

### Этап D — объединение Channel Points и специальных эффектов

1. Убрать дублирующий `twitch.reward.activated` транспорт, если он передаёт то же redemption.
2. Перевести side effects на обработку исходного redemption notification и обеспечить идемпотентность.
3. Перевести медиа-привязки на Twitch reward ID.
4. Убрать обязательный `AlertKey` и отвязать дневные правила от общего каталога наград.
5. Удалить старые consumers, bindings, protobuf cases, SignalR event names и клиентские заглушки, которые больше не используются.

### Этап E — проверка и очистка

1. Проверить создание награды напрямую в Twitch и через MARS.
2. Проверить неизвестный серверу тип EventSub: он должен пройти весь транспорт без нового C# класса.
3. Проверить повторную доставку, reconnect и повторную подписку.
4. Убедиться, что один redemption отображается ровно один раз и side effect не выполняется повторно.
5. Убедиться, что отсутствие локальной записи, `AlertKey`, медиа или специального эффекта не теряет само событие.
6. Удалить неиспользуемые типизированные DTO и регистрацию только после проверки ссылок по всему solution.

## 10. Критерии готовности

- В общем пути доставки нет `ConcurrentDictionary<string, Type> _eventTypes` и аналогичного реестра типов.
- Twitch EventSub JSON проходит от TwitchCore до ClientApp без десериализации `payload.event` в отдельные C#-классы.
- Сервер использует один общий RabbitMQ маршрут и один общий способ доставки в TelegramusHub/SignalR.
- Нет отдельных методов/контрактов доставки Follow, VIP, Raid, StreamOnline или RewardActivated.
- Новый `subscription_type` не требует изменения C#, protobuf, RabbitMQ routing или SignalR.
- ClientApp разбирает JSON и может отобразить Channel Points redemption без `AlertKey`.
- Неизвестный тип не ломает транспорт; для него действует общий fallback.
- Специальные эффекты работают как необязательные side effects, а не как условие доставки.
- Одно EventSub notification не обрабатывается параллельно старым и новым конвейерами.
- Повторная доставка не приводит к дублированию показа или побочного действия.

## 11. Что не является целью

- Не нужно заранее создавать C#-модель для каждого EventSub типа.
- Не нужно создавать отдельный метод TelegramusHub, protobuf case или SignalR event для каждого типа.
- Не нужно подписываться на все доступные Twitch события. Подписываемся только на те, которые реально нужны MARS; транспорт умеет прозрачно передавать любое полученное notification.
- Не требуется автоматически придумывать специальную анимацию для неизвестного события. Для этого остаётся общий fallback, а уникальное отображение при необходимости добавляется на клиенте.
