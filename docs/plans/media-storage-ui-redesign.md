# План переработки UI MARS.MediaStorage

**Статус:** запланировано  
**Область:** MARS.MediaStorage — файловый браузер, предпросмотр и миграция UI  
**Целевая ветка:** main  
**Связанный PR:** [#75 — раздача текущего Storage UI в dev Compose](https://github.com/RXDCODX/MARS/pull/75) — уже влит  
**Документ не меняет поведение приложения.** Это план реализации, разбитый на самостоятельные PR.

---

## 1. Цель и ожидаемый результат

Заменить текущую таблицу файлов полноценным файловым браузером, встроенным в ASP.NET Core MARS.MediaStorage.

Пользователь должен иметь возможность:

1. Перемещаться по реальной структуре wwwroot, включая пустые каталоги.
2. Видеть дерево папок слева, текущий каталог справа и навигационные хлебные крошки.
3. Не видеть отдельную колонку с полным путём к файлу.
4. Открывать файл в панели предпросмотра, не покидая файловый браузер.
5. Продолжать выполнять все существующие операции хранилища: загрузку, перенос, мягкое удаление, восстановление, индексацию и выборочную Git-синхронизацию.
6. Получать обновления дерева и списка при изменениях на диске.
7. Работать по тому же внешнему адресу через Gateway: /storage-ui/index.html.

Итоговая реализация не должна требовать отдельного React/Vite-приложения, Node.js в Docker-сборке или нового NuGet-пакета файлового менеджера.

## 2. Аудит текущего состояния

### 2.1. Что уже есть

Текущий UI находится в src/MARS.MediaStorage/ClientApp:

- React 19 + TypeScript + Vite;
- @microsoft/signalr для обновления списка;
- таблица с виртуализацией строк;
- фильтрация по имени и пути;
- миниатюры изображений и ссылки на открытие аудио/видео;
- загрузка нескольких файлов с прогрессом и drag-and-drop;
- перенос, мягкое удаление и восстановление;
- dry-run для массовых операций;
- ручная индексация;
- Git status и выборочная синхронизация файлов.

Основная логика интерфейса находится в ClientApp/src/App.tsx, API-клиент — в ClientApp/src/api.ts.

Серверная часть уже предоставляет:

| Endpoint | Назначение |
|---|---|
| GET /api/MediaStorage/entries | Список индексированных записей, включая опциональную корзину |
| GET /api/MediaStorage/git/status | Состояние Git |
| POST /api/MediaStorage/index | Индексация файлов |
| POST /api/MediaStorage/upload | Загрузка нескольких файлов |
| POST /api/MediaStorage/move | Массовый перенос |
| POST /api/MediaStorage/delete | Мягкое удаление |
| POST /api/MediaStorage/restore | Восстановление |
| POST /api/MediaStorage/sync | Выборочная Git-синхронизация |
| GET /api/MediaStorage/file | Отдача файла по относительному пути |

MediaStorageController.GetFile уже проверяет относительный путь, блокирует содержимое _trash и включает enableRangeProcessing. Это хорошая основа для preview, но контракт предпросмотра и безопасное поведение Content-Disposition нужно закрепить отдельными тестами.

### 2.2. Почему текущая модель не показывает папки

Сейчас таблица строится из MediaStorageEntry, то есть из файлов, проиндексированных в PostgreSQL.

У этой модели нет сущности каталога. Поэтому:

- пустая папка не попадёт в UI;
- папка, в которой ещё нет индексированных файлов, не появится;
- наличие каталога нельзя надёжно вывести из списка записей БД;
- физические изменения на диске и состояние индекса могут временно расходиться.

Нельзя решать это построением дерева только из StorageEntry.path: такой подход никогда не покажет пустые каталоги.

### 2.3. Текущие ограничения FileSystemWatcher

MediaStorageFileWatcher уже наблюдает за wwwroot, вызывает IndexAsync, а при изменении индекса отправляет StorageChanged через SignalR. Есть debounce и периодическая сверка раз в минуту — это важно для Docker bind mount, в частности при работе с Windows-диском.

Но текущая реализация не покрывает изменение структуры каталогов:

- ShouldObserve сразу отбрасывает путь, если File.Exists возвращает false; для каталогов это условие истинно;
- обработчик Deleted не зарегистрирован;
- уведомление StorageChanged отправляется только при Added > 0 или Updated > 0;
- создание пустой папки не меняет индекс файлов и поэтому не приводит к обновлению UI.

Для дерева папок потребуется отдельный сигнал изменения структуры, а не только сигнал об изменении файлового индекса.

### 2.4. Развёртывание

PR #75 уже влит в main (merge commit bdc96baa5d8b0d15a4b585835c51d462fdddab35). Сейчас он обеспечивает наличие Vite-статики и в dev-контейнере.

Это исправление нужно сохранить до полного перехода на новый UI. Удалять Node stage, StorageUi:Root и StorageUi__Root следует только в заключительном PR, после достижения функционального паритета.

Критичное ограничение: wwwroot — это обязательный bind mount с Git-рабочей копией пользовательских медиафайлов. UI-ассеты нельзя класть в этот каталог: они начнут попадать в файловый индекс и Git-репозиторий хранилища.

## 3. Архитектурное решение

### 3.1. Выбранный вариант

**ASP.NET Core Razor Pages + небольшой vanilla JavaScript.**

Razor Pages отвечает за HTML, навигацию, серверную валидацию и первичное отображение страницы. Небольшой JS-модуль отвечает только за интерактивные части:

- раскрытие узлов дерева;
- выбор файла и обновление панели preview;
- вызовы существующих API массовых операций;
- прогресс загрузки;
- SignalR;
- обновление списка без полной перезагрузки там, где это оправдано.

Новый UI размещается в MARS.MediaStorage.Host, а не в отдельном клиентском приложении.

### 3.2. Почему не SimpleFileBrowser

[Репозиторий SbGibson/SimpleFileBrowser](https://github.com/SbGibson/SimpleFileBrowser) содержит browse.aspx и browser.ascx. Это Web Forms / ASP.NET Web Site-компонент, а не готовая библиотека файлового менеджера для ASP.NET Core Razor Pages. Перенос такого компонента в текущий .NET 10 Host означал бы фактически переписывание его логики.

Использовать его как зависимость проекта не следует.

### 3.3. Почему не достаточно DirectoryBrowserMiddleware

Статья [Code Maze про Directory Browsing в ASP.NET Core](https://code-maze.com/aspnetcore-directory-browsing/) показывает AddDirectoryBrowser / UseDirectoryBrowser.

Этот middleware полезен для простого диагностического просмотра каталога, но не решает задачи MediaStorage:

- не предоставляет нужный интерфейс дерева с ленивым раскрытием;
- не объединяет файловую систему с метаданными MediaStorageEntry;
- не реализует preview pane;
- не поддерживает текущие операции над записями, dry-run и выборочную Git-синхронизацию;
- не даёт нужного контроля над тем, какие файлы и каталоги показывать.

Кроме того, Microsoft отдельно предупреждает, что UseDirectoryBrowser и UseStaticFiles могут раскрывать содержимое директорий и что directory browsing в production обычно следует отключать. См. [официальную документацию ASP.NET Core](https://learn.microsoft.com/aspnet/core/fundamentals/static-files?view=aspnetcore-10.0).

**Не включать UseDirectoryBrowser на всём wwwroot.** Нужен собственный ограниченный browser endpoint, который возвращает только разрешённые данные.

### 3.4. Где хранить UI-ассеты

Запрещено размещать CSS/JS нового интерфейса в media wwwroot.

Предлагаемая структура:

~~~text
src/MARS.MediaStorage/MARS.MediaStorage.Host/
├── Pages/
│   ├── _ViewImports.cshtml
│   ├── _ViewStart.cshtml
│   └── Storage/
│       ├── Index.cshtml
│       ├── Index.cshtml.cs
│       └── Shared/
│           ├── _Toolbar.cshtml
│           ├── _FolderTree.cshtml
│           ├── _FileList.cshtml
│           └── _PreviewPane.cshtml
├── StorageUiAssets/
│   ├── storage-ui.css
│   └── storage-ui.js
├── Services/
│   └── MediaStorageFileWatcher.cs
└── Program.cs
~~~

StorageUiAssets раздаётся отдельным StaticFileOptions с отдельным PhysicalFileProvider и отдельным URL-префиксом, например /storage-ui/assets. Каталог должен лежать под ContentRootPath, но вне media WebRootPath.

Ассеты нужно включить в output/publish через настройки CopyToOutputDirectory / CopyToPublishDirectory. В dev они должны быть доступны из исходников без отдельной npm-сборки.

Razor Pages регистрируются через AddRazorPages() и MapRazorPages().

### 3.5. Совместимость URL

Внешний адрес не меняется:

- основной entry point — /storage-ui/index.html;
- /storage-ui и /storage-ui/ можно перенаправлять на основной entry point;
- Gateway/YARP продолжает проксировать /storage-ui/{**remainder};
- ссылки на /api/MediaStorage/* и /hubs/media-storage остаются под теми же префиксами.

На этапе разработки новая страница сначала доступна по временной ссылке /storage-ui-next. Переключать существующий URL на Razor Pages разрешается только после прохождения чек-листа функционального паритета.

## 4. Модель данных файлового браузера

### 4.1. Два источника данных

| Данные | Источник истины | Причина |
|---|---|---|
| Каталоги и их вложенность | Файловая система WebRootPath | В БД нет сущности каталога, пустые папки должны отображаться |
| Наличие физического файла | Файловая система WebRootPath | Файл может быть положен напрямую на диск |
| Размер и время изменения на диске | Файловая система | Эти значения должны быть доступны и до индексации |
| ID, media type, дата загрузки, дата последней выдачи, состояние удаления | PostgreSQL / MediaStorageEntry | Это учётные метаданные и ключи существующих операций |
| Git status | IMediaGitService | Git-рабочая копия — тот же обязательный host volume |

Не заводить таблицу каталогов в PostgreSQL только ради отображения дерева. Она дублировала бы состояние файловой системы и требовала бы отдельной синхронизации.

### 4.2. Правила отображения

- В обычном режиме браузер показывает физические каталоги и физические файлы внутри wwwroot.
- Пустые каталоги показываются всегда.
- Файлы сопоставляются с MediaStorageEntry по каноническому относительному пути.
- Для файла без записи в БД показывается статус «Не индексирован». Его можно открыть/скачать, но операции, которым нужен Guid записи, недоступны до индексации.
- Когда watcher индексирует такой файл, UI обновляет строку и включает операции.
- Файловый браузер не должен скрывать физический файл только потому, что его запись в БД ещё не появилась.
- В обычном дереве не показываются .git, _trash и скрытые каталоги/файлы, начинающиеся с точки. Правила должны совпадать с фильтрацией индекса.
- Корзина остаётся отдельным представлением на основе ListAsync(includeDeleted: true). Содержимое _trash не появляется в обычном дереве и не может быть открыто через preview.
- Физически удалённый вне приложения файл не следует автоматически превращать в мягко удалённый. Семантика внешнего удаления — отдельное решение; этот план не меняет текущую модель удаления.

### 4.3. Контракт списка каталога

Добавить отдельный контракт файлового браузера. Названия DTO/сервисов предварительные, окончательные имена выбрать в соответствии с текущими соглашениями проекта.

Вариант ответа GET /api/MediaStorage/browse?directory=Alerts/random_meme:

~~~json
{
  "currentDirectory": {
    "name": "random_meme",
    "relativePath": "Alerts/random_meme"
  },
  "parentDirectory": "Alerts",
  "directories": [
    {
      "name": "videos",
      "relativePath": "Alerts/random_meme/videos",
      "hasChildren": false
    }
  ],
  "files": [
    {
      "name": "example.mp4",
      "relativePath": "Alerts/random_meme/example.mp4",
      "sizeBytes": 123456,
      "lastWriteTimeUtc": "2026-01-01T12:00:00Z",
      "storageEntryId": "00000000-0000-0000-0000-000000000000",
      "mediaType": 3,
      "isIndexed": true,
      "uploadedAt": "2026-01-01T12:00:00Z",
      "lastDownloadedAt": null
    }
  ]
}
~~~

Это иллюстрация формы контракта, а не предлагаемые реальные данные.

Требования к endpoint:

- возвращает только непосредственных потомков указанного каталога;
- не рекурсирует по всему архиву на каждый запрос;
- возвращает каталоги отдельно от файлов;
- каталоги сортируются по имени без учёта регистра, затем файлы по имени;
- пути в JSON канонические: относительные, без ведущего /, с / как разделителем;
- для неизвестного каталога возвращает 404, для некорректного пути — 400;
- пустой directory означает корень wwwroot;
- никогда не возвращает абсолютный путь хоста или контейнера.

Для дерева использовать ленивую загрузку. При раскрытии папки UI запрашивает её непосредственных дочерних каталогов; не нужно формировать и передавать всё дерево целиком.

### 4.4. Сопоставление файлов с метаданными

Сопоставление делать по нормализованному пути, а не по имени файла: одинаковые имена в разных каталогах допустимы.

Для обычного каталога нужны метаданные только файлов этого каталога. Предпочтительно добавить в storage service метод выборки по директории/префиксу, чем вызывать ListAsync() и фильтровать всю таблицу на каждый запрос раскрытия дерева.

При этом существующий ListAsync(includeDeleted) сохраняется для корзины и совместимости. Не менять публичную семантику уже существующих API ради новой страницы.

## 5. UX и поведение интерфейса

### 5.1. Основной экран

~~~text
┌─────────────────────────────────────────────────────────────────────┐
│ Хранилище медиа   Git: main · 3 изменения   [Обновить] [Загрузить]  │
│ [Поиск по имени и содержимому каталога] [Индексировать] [Корзина]   │
├──────────────────┬──────────────────────────────────────────────────┤
│ Каталоги         │ Главная / Alerts / random_meme                   │
│                  ├──────────────────────────────────────────────────┤
│ ▾ Alerts         │ [ ] Тип   Имя                 Размер   Загружен   │
│   ▾ random_meme  │ [ ] 📁    videos                         —        │
│     videos       │ [ ] 🎬    clip.mp4           12 МБ     01.11.26   │
│   uploads        │ [ ] 🖼    cover.jpg          1.2 МБ    01.11.26   │
│ ▸ TTS            │ [ ] 📁    empty-folder                  —        │
│                  │                                                  │
│                  │                                                  │
├──────────────────┴──────────────────────────────────────────────────┤
│ Нижняя/правая панель предпросмотра открывается при выборе файла      │
└─────────────────────────────────────────────────────────────────────┘
~~~

На широком экране — три рабочие зоны: дерево, список, preview pane. Preview pane может занимать правую часть или открываться как выдвижная панель. На узком экране дерево и preview становятся переключаемыми панелями/модальными слоями.

### 5.2. Навигация

- Убрать колонку Путь из таблицы.
- Не выводить полный путь в title, tooltip или дополнительном текстовом поле строки.
- Для ориентации использовать хлебные крошки: Главная / Alerts / random_meme.
- Каждый сегмент breadcrumb кликабелен и ведёт в соответствующий каталог.
- Клик по каталогу открывает его; клик по файлу выбирает файл и открывает preview.
- Раскрытие дерева не должно автоматически менять выбранный каталог.
- Состояние текущего каталога сохраняется в query string, чтобы работали Back/Forward и прямые ссылки.
- После переключения каталога сбрасывается выбор файлов, если они больше не принадлежат текущему представлению.
- В дереве отображаются пустые каталоги.
- Поиск остаётся глобальным по индексированным файлам, как сейчас. Результат поиска показывает имя и доступную навигацию к родительскому каталогу, но не отдельную колонку с полным путём.

### 5.3. Таблица каталога

Колонки:

1. Checkbox выбора.
2. Тип/иконка и небольшой thumbnail для изображений.
3. Имя файла.
4. Размер.
5. Загружен.
6. Последний раз открыт.
7. Индикатор индексации/состояния — только если он полезен пользователю.

Не дублировать в таблице путь, расширение и имя одновременно, если расширение уже входит в имя файла.

Сортировка по имени и размеру желательна. Папки всегда располагаются перед файлами.

Текущая React-таблица виртуализирует строки из-за большого количества записей. Новый UI должен не возвращаться к неограниченному DOM:

- endpoint возвращает только текущий каталог;
- для очень больших каталогов использовать постраничную выдачу или виртуализацию;
- глобальный поиск ограничить серверной выдачей/пагинацией, если объём индекса станет заметным;
- не загружать все физические файлы всего wwwroot при каждом раскрытии папки.

### 5.4. Предпросмотр

Preview открывается при выборе файла и не должен менять текущий каталог.

Поддерживаемые типы:

| Тип | Представление | Условия |
|---|---|---|
| PNG, JPEG, WebP, GIF, AVIF | Изображение | Ограничить размер визуальной области, object-fit: contain |
| MP4, WebM и другие поддерживаемые video MIME | video controls | HTTP Range обязателен для нормальной перемотки |
| MP3, OGG, WAV и другие поддерживаемые audio MIME | audio controls | HTTP Range желателен |
| PDF | Встроенный просмотрщик браузера | Только при безопасном application/pdf |
| TXT, LOG, JSON, XML, CSV, Markdown | Текстовая панель | Отдавать как текст, экранировать; ограничить объём чтения |
| HTML, JS, SVG и неизвестные бинарные форматы | Без inline-preview | Только метаданные и скачивание |

Дополнительные детали:

- Видео и аудио не должны скачиваться целиком до начала воспроизведения.
- Для больших файлов использовать preload="metadata" либо preload="none".
- Для изображения показывать фактические размеры, если они известны; не загружать несколько копий одного preview.
- Для текстового preview установить верхний лимит, например 512 KiB, и сообщать, что содержимое обрезано.
- Не выполнять содержимое файла как HTML/JS.
- Не вставлять непроверенный текст через innerHTML.
- Для неизвестного типа показывать расширение, MIME, размер, дату изменения и кнопку «Скачать».
- Ошибка preview не должна ломать список и дерево.
- Для очень больших изображений предусмотреть ограничение размеров отображения, но не создавать серверные thumbnails в рамках первой итерации.

### 5.5. Существующие операции

Новая реализация обязана сохранить текущие возможности:

| Возможность | Ожидаемое поведение |
|---|---|
| Загрузка | Несколько файлов, выбор целевого каталога |
| Drag-and-drop | Загрузка файлов в открытый каталог |
| Прогресс загрузки | Процент и объём переданных данных |
| Индексация | Запустить POST /index, затем обновить текущий список |
| Перенос | Массово перемещать выбранные индексированные файлы |
| Dry-run | Показывать результат пробной операции без изменения данных |
| Корзина | Переключение на удалённые записи |
| Восстановление | Восстанавливать выбранные записи; обрабатывать конфликт существующего файла |
| Git status | Показывать ветку, pending paths и ошибку проверки |
| Git sync | Синхронизировать только выбранные индексированные файлы |
| Результат операции | Показывать requested/succeeded/failed и список ошибок |

Действия, требующие MediaStorageEntry.Id, отключены для неиндексированных физических файлов. Для них доступна индексация/ожидание watcher, просмотр и скачивание.

Загрузка по умолчанию направляется в открытый каталог, если пользователь явно не выбрал другой. Перенос также должен предлагать дерево каталогов, а не требовать от пользователя вручную вводить строку пути.

## 6. Backend: сервис файлового браузера

### 6.1. Ответственность

Добавить отдельную абстракцию для чтения физической структуры хранилища. Не раздувать IMediaStorageService обязанностями обхода директорий, если это можно изолировать.

Вариант разделения:

- application contract: интерфейс browser service и DTO;
- infrastructure implementation: безопасная работа с физической файловой системой;
- MediaStorageController: HTTP endpoints и перевод результата в OperationResult<T>;
- Razor Page: серверная оболочка и первичное отображение.

Конкретное расположение интерфейса и реализации согласовать с фактическими зависимостями проектов перед кодированием.

### 6.2. Безопасное разрешение каталогов

Вся работа ведётся только относительно IWebHostEnvironment.WebRootPath.

Алгоритм для пользовательского directory:

1. Нормализовать разделители через существующую MediaPath.Normalize.
2. Отклонить пустые сегменты, . и .. там, где они недопустимы.
3. Отклонить rooted/absolute пути, drive letters, UNC и нулевые байты.
4. Сформировать полный путь через Path.GetFullPath.
5. Проверить, что результат лежит внутри canonical root с корректным разделителем и сравнением, учитывающим ОС.
6. Не обходить symlink/reparse point и не заходить через них за пределы хранилища.
7. Повторять проверку на каждой операции открытия файла — результат проверки списка не является разрешением на последующее чтение.

Нельзя ограничиваться только StartsWith(root): префиксы каталогов могут совпасть (/data/wwwroot-evil). Сравнение выполняется с root + DirectorySeparatorChar, а сам root обрабатывается отдельно.

Для корневого каталога разрешено пустое значение. Для дочерних путей возвращать только относительные формы с /.

### 6.3. Исключения из обхода

Не показывать и не сканировать:

- .git;
- _trash;
- любые сегменты, начинающиеся с точки;
- symbolic links / reparse points;
- каталоги, не проходящие проверку нахождения внутри корня.

Фильтрацию нужно вынести в одну общую политику, чтобы дерево, список и watcher не расходились по правилам.

Не использовать SearchOption.AllDirectories без контроля symlink и исключаемых каталогов.

### 6.4. API файлового браузера

Предлагаемые новые endpoints:

| Endpoint | Назначение |
|---|---|
| GET /api/MediaStorage/browse?directory= | Непосредственные каталоги и файлы выбранного каталога |
| GET /api/MediaStorage/search?q= | Глобальный поиск по индексированным файлам с ограниченной выдачей |
| GET /api/MediaStorage/preview?path= | Безопасное inline-представление разрешённых preview MIME |
| GET /api/MediaStorage/text-preview?path= | Ограниченное по размеру текстовое содержимое |

Существующие операции не переименовывать и не менять без необходимости.

GET /api/MediaStorage/file сохранить для обратной совместимости. Его текущий смысл и заголовки проверить тестом; не полагаться на предположение, что браузер всегда покажет файл inline.

Для предпросмотра явно разделить inline и download поведение. Необходимо либо оставить /file скачиванием и добавить отдельный /preview, либо ввести строго ограниченный параметр disposition. Предпочтительнее отдельные endpoint-ы с однозначной семантикой.

### 6.5. HTTP и MIME

Для media preview:

- отдавать MIME из серверного allowlist, а не доверять Content-Type, пришедшему при загрузке;
- разрешать Content-Disposition: inline только для явно поддержанных типов;
- enableRangeProcessing: true для больших media-файлов;
- поддержать Range и проверять ответ 206 Partial Content;
- выставлять X-Content-Type-Options: nosniff;
- неизвестные расширения и активное содержимое отдавать только как attachment или plain text;
- не разрешать inline HTML, JavaScript и SVG в первой версии.

Для текстового preview читать ограниченное число байт/символов и явно сообщать об усечении. Не загружать произвольный многогигабайтный текстовый файл целиком в память.

### 6.6. Ошибки

- 400 — некорректный относительный путь или параметр;
- 404 — каталог/файл отсутствует либо не виден в данном представлении;
- 413 — превышен допустимый размер текстового preview, если endpoint выбран с жёстким лимитом;
- 415 — формат не поддерживается для preview;
- 500 — неожиданный сбой, без раскрытия абсолютных путей и внутренней структуры контейнера.

Существующий API использует OperationResult<T> и в ряде случаев возвращает бизнес-ошибку с HTTP 200. Новые endpoints должны следовать существующему контракту проекта там, где это уместно, но не скрывать ошибки безопасности за успешным HTTP-статусом.

## 7. Обновление UI через SignalR и watcher

### 7.1. Разделить два вида изменений

Не смешивать «изменился индекс файлов» и «изменилась структура каталогов».

Вариант событий:

- StorageChanged — индекс файлов изменился; клиент обновляет метаданные и список.
- StorageStructureChanged — изменились каталоги/физическая структура; клиент обновляет дерево и текущий список.

Можно оставить единый event с changeKind, но контракт должен однозначно различать изменения.

### 7.2. Исправить FileSystemWatcher

- Подписать watcher на Deleted.
- Различать события для файлов и каталогов.
- Не использовать File.Exists как единственный критерий наблюдения.
- Для каталогов учитывать Directory.Exists, а также тип события Renamed/Deleted, когда объекта уже нет.
- Создание/переименование/удаление папки должно инициировать refresh структуры, даже если индекс файлов не изменился.
- Изменение файла должно инициировать debounce + IndexAsync, как сейчас.
- Исключения .git, _trash и скрытых сегментов должны применяться и к папкам, и к файлам.
- При overflow буфера запускать полную сверку.

### 7.3. Периодическая сверка

Не полагаться на FileSystemWatcher как на гарантированный механизм: Docker Desktop может не доставлять inotify-события из Windows bind mount в Linux-контейнер.

Сохранить периодическую сверку раз в минуту как fallback. Для дерева нужно обнаруживать изменение структуры даже тогда, когда индекс файлов не поменялся. Реализация может использовать сравнение снимка/отпечатка структуры или отдельную сверку каталогов.

Не отправлять SignalR событие каждую минуту без изменений только ради heartbeat. Клиент должен иметь ручное обновление дерева на случай пропущенного сигнала.

UI должен:

- подписываться на оба вида изменений;
- переподключаться после разрыва SignalR;
- обновлять текущий каталог без сброса выбора, если выбранный файл всё ещё присутствует;
- закрывать preview, если файл исчез или перестал быть доступен;
- не заявлять о мгновенном обновлении в окружениях, где доступны только периодические сверки.

## 10. Нефункциональные требования и защита

1. **Никакого доступа за пределы WebRootPath.** Любой путь из HTTP считается недоверенным.
2. **Symlink/reparse points не обходятся.** Проверка должна применяться как к каталогу, так и к файлу на этапе preview/download.
3. **Не раскрывать абсолютные пути.** Ни в HTML, ни в JSON, ни в сообщениях ошибок.
4. **Не включать directory browsing глобально.** Browser API выдаёт ограниченный DTO, а не открывает файловую систему как публичный каталог.
5. **Не выполнять загруженное содержимое.** HTML/JS/SVG не открываются как активный документ.
6. **Не помещать UI-ассеты в media volume.**
7. **Не читать крупные файлы в память целиком.** Media отдаётся потоком с Range; text preview имеет строгий лимит.
8. **Не терять существующие контракты.** Текущие API операций, Hub URL и Gateway route остаются совместимыми.
9. **Не плодить новые зависимости.** Razor Pages и обычный JS достаточно; новый UI framework и файловый менеджер не добавлять.
10. **Логировать проблемы watcher и preview**, но без полного пути пользовательского хоста и содержимого файлов.

## 11. Что не входит в первую версию

Чтобы не превратить файловый браузер в отдельный файловый сервер, пока не реализуем:

- создание, переименование и удаление каталогов как самостоятельные операции;
- копирование каталогов;
- массовое скачивание ZIP;
- серверное создание thumbnail-кэша;
- встроенный редактор файлов;
- inline-просмотр HTML, SVG и исполняемых файлов;
- изменение Git-структуры каталога из дерева;
- новую таблицу PostgreSQL для каталогов;
- автоматическое превращение внешнего удаления файла в soft delete.

Эти функции можно отдельно оценить после появления базового браузера.

## 12. Риски и решения, требующие внимания

| Риск | Мера |
|---|---|
| В wwwroot находятся одновременно media и Git-рабочая копия | UI-ассеты держать в ContentRootPath/StorageUiAssets, раздавать отдельным provider |
| Пустые каталоги не существуют в БД | Дерево строить по физической ФС |
| FileSystemWatcher теряет события в Docker Desktop | Debounce + периодическая сверка + ручной refresh |
| Symlink позволяет выйти за корень | Не следовать ссылкам, проверять canonical path на каждой операции |
| Content-Disposition мешает preview | Отдельный inline endpoint и тест заголовков |
| SVG/HTML может содержать активный контент | Не разрешать их inline |
| Большой архив перегружает HTML/браузер | Lazy tree, листинг только текущей папки, ограниченный поиск/пагинация |
| Удаление React ломает загрузку/перенос/Git sync | Cutover только после parity checklist |
| Старый Docker build всё ещё копирует Vite output | Удалять Node stage только в последнем PR |
| Событие watcher приходит в середине копирования | Debounce, проверка существования/стабильности файла и повторная сверка |

## 13. Definition of Done

Работа считается законченной, когда одновременно выполнено следующее:

- [ ] /storage-ui/index.html обслуживается Razor Pages, а не Vite.
- [ ] В левой панели отображается реальная структура каталогов, включая пустые.
- [ ] Дерево раскрывается лениво и не показывает .git, _trash, скрытые папки и symlinks.
- [ ] Текущая папка видна через breadcrumbs.
- [ ] Колонки полного пути больше нет.
- [ ] Есть рабочий global search.
- [ ] Preview открывает поддерживаемые изображения, GIF, аудио, видео и PDF.
- [ ] Текстовые preview ограничены по размеру и не исполняются как HTML.
- [ ] Range-запросы корректно работают для видео/аудио.
- [ ] Все текущие операции старого UI сохранены.
- [ ] Неиндексированные файлы не ломают bulk actions.
- [ ] Создание/переименование/удаление каталогов обновляет дерево; периодическая сверка покрывает потерянные FS events.
- [ ] Dev и production Docker images работают без Node/Vite.
- [ ] Ни один UI-ассет не попадает в media wwwroot.
- [ ] Тесты MediaStorage и проверки Gateway проходят в CI.
- [ ] Документация отражает новый UI и его endpoint-ы.

## 14. Порядок выполнения

Рекомендуемый порядок PR:

1. feat(media-storage): add filesystem browser API — безопасный backend-листинг.
2. fix(media-storage): publish storage structure changes — watcher и SignalR для каталогов.
3. feat(media-storage): add Razor storage browser — дерево, breadcrumbs, список, поиск.
4. feat(media-storage): add inline media preview — preview API и панель.
5. feat(media-storage): preserve storage operations in Razor UI — функциональный паритет.
6. refactor(media-storage): remove React storage client — переключение URL и удаление Vite/Node.
7. Финальная эксплуатационная проверка и документация.

PR-ы 1–5 не должны удалять текущий React UI и не должны ломать /storage-ui/index.html. Это произойдёт только при cutover в PR 6.
